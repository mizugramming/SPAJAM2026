# 修正記録を次の判断に使う

## 根拠を受け取る

`AGENTS.md`、READMEが示す現行資料、提供記録、反映先の関連部分を読む。未提供チャットへアクセスできる前提を置かない。記録がなければ受領待ちとし、修正理由を作らない。実装から分かる現在の挙動は、過去の承認や原因の証拠と分ける。

原記録を保持し、出典のファイル・節・記録IDを付ける。秘密情報は転記しない。繰り返された指摘は同じ原因・条件か確認して統合し、数だけで必須ルールにしない。

## 5項目で抽出する

| 項目 | 記載のしかた |
|---|---|
| 指摘内容 | 誰のどの操作・状態で何が問題だったか。出典 |
| 問題の原因 | 実コード・再現で確認した事実／記録内の説明／推測／不明を明記 |
| 採用した修正 | 採用・検証の証拠。提案のみ、却下、理由不明は区別 |
| 適用する条件 | 再利用できる条件、そのアプリだけの仕様・好み、適用しない場合 |
| 次回の確認方法 | 再現する操作・状態と期待結果。何を見れば防げるか |

原因不明でも、確認できる指摘と採用修正は残せる。推測を埋めるためだけに全作業を止めない。解釈が必須ルールや既存仕様を変える場合だけ、必要な質問をまとめる。

## 一つの正本へ反映する

- **Skills**：条件のある再利用手順・判断・検証方法。知見は該当する手順へ短く統合する。
- **AGENTS.md**：日常的に全担当が守る共同作業の約束。アプリ固有の色・寸法・報酬・SDK値を入れない。
- **アプリ資料**：そのアプリの文言、見た目、保存仕様、端末条件、採否と理由。

既存ルールと意味・適用条件を照合し、同じ知見は既存箇所を改善する。詳細な事例・原文は記録に残し、各指示へ全文コピーしない。採用されなかった案、理由不明の変更、特定アプリの好みを汎用の禁止・必須にしない。廃止案は履歴へ退け、現行指示を矛盾させない。

台帳は既存資料を使い、なければ `docs/retrospectives/lessons.md` に置く。列は `ID・出典 / 指摘 / 原因と確度 / 採用修正と確認状況 / 適用条件 / 次回確認 / 反映先`。原記録と台帳の説明を重複させない。

## 反映を確かめる

1. 各変更に根拠と条件があり、既存合意と衝突せず、読まれる場所から参照できるか確認する。
2. 短い別アプリ案か同じ失敗条件に手順を当て、期待する判断と適用しない判断を具体的に試す。実施できない実機・画像確認は成功扱いしない。
3. Skill変更時はリポジトリの検証コマンドで形式・参照を確認する。変更した補助スクリプトは実行する。
4. 反映先、統合した重複、見送った項目と理由、検証・未確認を報告する。

記録の整理依頼を、現行アプリのコード修正・依存更新・公開・GitHub投稿への許可へ広げない。具体的な修正も依頼された場合は、最新仕様と担当範囲を確認して進める。
