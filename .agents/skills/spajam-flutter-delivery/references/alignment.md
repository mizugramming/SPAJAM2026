# 認識合わせ

## 既知の情報から短く収束する

会話・現行資料から次を先に埋める。既知の項目は質問しない。

| 整理するもの | 実装判断につなげる内容 |
|---|---|
| 誰が・いつ・どこで使うか | 利用者、片手・屋外・会場などの場面、利用時間 |
| 課題と体験 | 何に困り、使った後に何が変わるかを一文で |
| 主要導線 | 起動 → 最初の行動 → 中心の操作 → 結果 → 次の行動。現実の行動とアプリの操作も分ける |
| 範囲と対象外 | 本選で実際に動かす機能、仮データ・演出の扱い |
| デザイン | 感じてほしい印象と利用上の理由。参考がなければ具体案 |
| サービス・端末 | 対象OS、台数、通信、カメラ等の機能、認証と権限 |
| 制約 | 残り時間、人数・担当、手元のSDK・端末、費用や利用枠 |
| 大会条件 | 資料の対象大会・日付・出典、確認済み事項と未確認事項 |

制限時間、持ち込みコード・Skills・素材・外部サービスの利用可否、提出条件を例年の記憶から確定しない。今回提供された資料を確認し、判断に必要なら公式情報を調べて出典と確認日を残す。規約が特定できなければ未確認とし、独立した準備を続ける。

質問は、主要体験・データ消失・対象OS・実装可否・完了判定を左右する不足だけ、関連項目をまとめて聞く。提案で進められるものには推奨案と理由を付ける。「状態管理は何にしますか」のような実装選択を丸投げしない。

例：保存が重要なのに未指定なら「再起動後も残す想定ですか。1台で使う案なら端末保存を提案します」と聞く。角丸やフォルダ名は質問項目にしない。

## コードの前の合意

次の短い形で、理解と提案を区別して提示する。

> 対象・場面：…。提供する体験：…。主要導線：A → B → C。
> 完成条件：利用者が…でき、別の開発者が…を再現できること。
> 対象外：…。提案する見た目と理由：…。決める必要がある点：…。

質問・合意要求を送ったら、依存するコードは回答後に着手する。同じコンセプト・導線・完成条件が既に合意済みなら、合意箇所を示して続ける。毎段階の承認会議を増やさない。

合意を設計書へ残す。合意後の変更では、現在有効な決定を更新し、撤回案を必須条件として積み上げない。

## 完成条件を観察できる形にする

- 各操作で何が表示・保存・更新され、失敗時に何が残るかを記す。
- 実サービスで動く範囲と合意した仮データ・ローカル動作を区別する。未実装の共有を成功表示で代用しない。
- 動く体験に加え、デザイン基準・共通部品・データの正本・機能境界と、会話不要の起動・担当引き継ぎを含める。
- 「全体がきれい」「実機対応済み」ではなく、操作、期待結果、確認方法、実施環境を対応付ける。
