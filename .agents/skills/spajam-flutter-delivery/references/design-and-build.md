# コンセプトを設計と初期実装へつなぐ

## 最小の構成と共有契約

1. 既存構成・必要機能・残り時間・チームの習熟から、状態と保存の正本を決める。画面内の編集値、画面をまたぐ確定状態、保存済みデータを区別する。既存の状態管理や保存処理があれば使う。
2. 画面・機能ごとに、目的、入口、主操作、結果、共有データの入出力を表にする。単純な構成で主要導線を一周させる。新規ライブラリ・MVVM・Repository・コード生成を一律必須にしない。
3. 並行作業の前に共有契約を記す。型と定義ファイル、ID、nullable、日時・単位、操作の引数と戻り値、成功・失敗・中断、保存形式、重複操作、変更通知、外部サービスの責任を必要な範囲で具体化する。
4. 共有モデル・テーマ・ルーター・親画面・依存関係・ロック・生成設定の担当を決める。機能はソース・素材・テスト単位で分け、同じ親ファイルを複数人へ渡さない。共有型・コールバック等でつなぎ、組み込みは親担当へ集約する。境界用の空階層を量産しない。

契約表の列例：`機能 / 定義・呼出元 / 入力 / 出力・通知 / 状態の正本 / 失敗時 / 管理担当`。利用側の短い例を添え、初期実装で実際に接続を通す。

## UI/UXと文言を同時に設計する

コンセプトから2〜3個の判断軸を選び、見た目と操作へ落とす。例えば「立ったまま片手で使う」は、大きな主操作、短い入力、即時反応へつなげる。参考画像の色・カード・装飾を無条件に移植しない。

配色・日本語書体・組版・構図の具体化と、アプリ固有の見せ方の点検には [UIの視覚基準](ui-review.md) を使う。採用理由と共通の基準はアプリの設計資料へ残し、テーマや部品の実装と揃える。

| 基準 | 設計する内容 |
|---|---|
| 色・文字 | 意味による色の役割、見出しと本文の優先順位、読みやすさ・コントラスト |
| 余白・形・アイコン | 情報のまとまり、押せる場所、主役と補助情報、アイコンのラベル |
| 操作・遷移・反応 | 主操作と補助操作、押した直後の反応、戻る・中断、完了後の行動 |
| 状態 | 通常、読み込み、空、入力エラー、通信・保存失敗、完了、無効。不要なら理由 |
| 共通化 | `ThemeData`・`ColorScheme`・`TextTheme`や既存テーマ、共通入力・ボタンの定義場所 |

各画面に「誰が何のために使うか / 主操作 / 状態ごとの表示と次の操作」を定める。各文言の読者と、理解・判断・操作のどれに役立つかを確認する。

- ラベルは実動作を表す。「送信」は送信する場合だけ使う。開始・受付・確定完了を混同しない。
- 会話内だけの用語、実装方針、開発中・引き継ぎの説明、根拠のない効果・数値、行動に役立たない飾り文は除く。必要な説明まで消さない。
- エラーは、起きたこと・入力が残るか・次にできることを短く伝える。権限は必要な理由と拒否時の代替を実装の範囲で案内する。
- 同じ結果からデータ・見た目・文言・音や演出を決める。前提がない成功文や、仮の操作による保存完了を出さない。
- 開発説明はREADMEや設計資料へ置く。文言が多い場合だけ場面・状態・表示条件を別表にし、正本を増やさない。

## 起動から実結果まで一周させる

まず起動 → 主要入力・操作 → 状態更新や保存 → 実結果表示 → 次の行動をつなぐ。画面ごとの見本だけで初期実装完了にしない。

外部接続が未準備なら、主要体験を損なわない代替を提案し、合意した境界で同じ契約の実装へ差し替える。複数端末の共有が中心なら、独立したローカル値で接続確認を済ませない。

連打、失敗時の入力保持、戻って再入力、保存・再読み込み・再起動の整合を確認する。非同期応答・タイマー・ライフサイクルがあれば責任と破棄を明確にする。接続後、見た目の確認と修正を行い、担当へ渡す。
