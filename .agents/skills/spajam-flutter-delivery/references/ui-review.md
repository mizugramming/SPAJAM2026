# UI/UXと操作部品を磨く

既存画面のUI/UX改善だけでも使う。対象をアプリ全体・画面・部品のどこまでとするか、指摘だけか修正までかを依頼から決める。ボタン1個の依頼を企画全体のやり直しへ広げない。

## 現物と目的を合わせる

現行のコンセプト・利用場面・主要導線、テーマと共通部品、対象画面の実装・文言・状態を読む。既にある判断軸を使い、コンセプトを聞き直さない。実画面と操作を確認し、コードだけでは分からない印象・押しやすさを確認済みとしない。

画面全体を見る場合は、最初に何が目に入り、利用者が何を理解して何を押し、その結果どこへ進むかを一周する。情報の優先順位・余白・文字量・視覚的な重心と、現実の利用場面を照合する。押せることだけで満足せず、色・文字・形・アイコン・動きの組み合わせが狙った印象につながるかを判断する。

## 色・書体・画面の調子を具体的に点検する

「親しみやすい」「洗練」等の印象を、採用する配色・書体・構図・素材へ結び付けて説明する。新しく方向を決める必要がある場合だけ、異なる具体案を同じ主要画面・実際の文言で比較する。合意済みの方向を毎回選び直さない。

| 対象 | 点検すること |
|---|---|
| 配色 | 背景・面・文字・主操作・強調・エラーの役割、色の面積と彩度、暖かさ/冷たさのまとまり。目立たせたい場所へ視線が向き、必要なコントラストを保てるか |
| フォント | コンセプトに合う日本語の字面と太さ、見出しと本文の組み合わせ、英数字・記号との釣り合い。指定の書体が実際に読み込まれ、別書体へフォールバックしていないか |
| 組版 | 実際の漢字・かな・英数字・長い名前で、サイズ・行間・字間・改行位置・揃えを確認。大見出しだけでなく本文・入力・ボタン・小さな補足も比較する |
| 余白・構図 | 主役の位置と大きさ、情報密度、整列、まとまり、画面内のリズム。内容の関係が読めるまとまりと、必要な強弱があるか |
| 形・素材・動き | 角丸・線・影・アイコンの太さ、写真やイラストの調子と前後関係、反応や遷移が一つの世界観としてつながるか |

変更前後は同じ入力・寸法・状態で実画面を見る。フォント名や色コードを書き換えただけで良くなったと判断しない。書体・素材の導入はプロジェクトの登録方法・利用条件と共通管理に従い、画面寸法や文字縮小で崩れを隠さない。

## アプリ固有の見せ方を育てる

「AIっぽい」という評価は、具体的な理由と改善対象へ分解する。例えば、コンセプトに関係のない装飾、同じ強さのカードの反復、根拠のない大きな数値、どこにでも使えるコピー、素材・文字・アイコンの調子の不一致を探す。角丸・グラデーション・カード・特定書体の一律禁止にはせず、各表現を使う理由を確認する。

- 利用者の場面と中心体験から、このアプリの主役になる構図・素材・情報の見せ方を選ぶ。その特徴を関連画面や操作への反応にもつなげる。
- 「この名前や主役の素材を別アプリへ差し替えても同じ提案か」「色や書体を選んだ理由を説明できるか」「装飾を外しても体験と次の行動が伝わるか」を見直す。明快な標準UIが適する機能は、その判断を尊重する。
- 独自性を出す箇所と、使い慣れた操作を保つ箇所を選ぶ。視認性・押しやすさ・状態の正確さもデザインの完成条件に含める。
- 個性のある初期案を作り、実画面で確認して細部を整える。違和感があれば配色だけでなく、構図・文字・素材・動きの関係へ戻って修正する。比較案を際限なく増やさない。

見た目の点検と、初見の人が魅力・意味・次の行動を理解したという検証は分ける。実施した比較と反応を記録し、「AIっぽさがなくなった」「好評だった」と根拠なく保証しない。

## 対象内の操作を一つずつ点検する

主ボタンだけでなく、戻る・閉じる・アイコンボタン・テキストリンク・一覧項目・切替・独自ジェスチャーも対象内で拾う。共通部品の同じ基準はまとめて確認し、文言・配置・状態が違う箇所は個別に見る。

| 観点 | 操作ごとに判断すること |
|---|---|
| 目的・主従 | 誰が何のために使うか。主操作と補助・破壊的操作が見分けられ、必要な位置で見つかるか |
| 文言・意味 | 押した後を予測できるか。「次へ」「OK」等で意味が曖昧なら、その場の動作が分かる案を出す。絵だけの操作にも名前を持たせる |
| 見た目 | コンセプトとテーマに合う色・文字の強さ・余白・形・アイコンか。主操作同士が競合せず、装飾が読取りを妨げないか |
| 操作性 | 見える形と実際のタップ領域、隣の操作との距離、片手操作、文字拡大・長いラベル・キーボード表示時の到達性を確かめる |
| 状態と反応 | 押した反応、フォーカス、必要な処理中・無効・完了・失敗が分かるか。すべての部品へ不要な状態を増やさない |
| 実処理 | ハンドラーの存在だけでなく遷移・更新・保存等の結果につながるか。連打・戻る・再試行で二重処理や入力消失が起きず、未実装の成功を装わないか |
| アクセシビリティ | 色だけに依存せず、文字が読め、意味・操作名・有効状態が読み上げ等へ伝わるか。対象で必要なフォーカス移動も確認する |

「全部を同じ大きさ・色へ揃える」を改善の目的にしない。共通化する基準と、主従や場面の違いで変える表現を分ける。曖昧な文言は意味を確かめて具体案を作り、既承認の語や操作の意味を勝手に変えない。

## 直して確かめる

1. 操作不能・誤操作や誤解、導線の迷い、コンセプトとの不一致、細部の順で影響を見て修正する。見た目の良さも扱い、色替えだけで完了にしない。比較が必要なら同じ入力・寸法・状態で具体案を示す。
2. 合意済みのデザインと操作の範囲では細部まで進める。意味や主要導線、共有契約・共通画面条件を変える場合は影響を示して調整する。共有部品の変更はAGENTS.mdの担当範囲に従う。
3. [画像の取得・再確認](verify-and-handoff.md#画面を見て修正する)に従い、修正前後を同条件で見る。対象操作を実際に押し、必要な状態と結果も確認する。画像だけで連打・保存・失敗時の挙動を確認したとしない。
4. 回帰リスクに応じて既存テストを使い、必要なら操作テストを足す。些細な装飾変更に実装を写したテストを増やさない。実機がなければ指での操作感・ネイティブ挙動は未確認として残す。

点検結果は既存の検証資料へ `画面・操作 / 目的と主従 / 根拠のある指摘 / 採用した変更 / 確認した状態・結果 / 未確認` で残す。全部品の同じ説明を長々と繰り返さず、ユーザーへの報告は主な改善と残る判断に絞る。

完了は、対象内の操作が目的・見た目・文言・反応・実結果の面で整合し、同じ条件で再確認できた範囲で判断する。「全ボタン確認済み」と言う場合は、対象と確認した操作・状態を記録する。
