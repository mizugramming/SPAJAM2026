# 既存アプリを開き、見えるところまで確認する

起動だけの依頼で企画・UI・プラットフォームを作り直さない。既存の画面を利用できることが目標。コマンド説明だけの依頼なら、環境に合う実際のコマンドを渡し、勝手にプロセスを起動しない。

## 起動する

1. `AGENTS.md`、READMEと現在の起動資料、最新の合意、以前の成功した方法を確認する。作業フォルダ・起動スクリプト・URLが現在も有効かを調べる。過去の一時フォルダを存在する前提にしない。
2. 必要な画面数と、Web・ネイティブ・エミュレーター等の実行先を文脈から特定する。「Flutter」という名称だけでWindows版の新設などへ飛躍しない。不足が完了条件を変える場合だけ短く確認する。
3. 対象アプリ・指定端末や専用プロファイルに限定して既存のコマンドを実行する。固定SDK・依存ロックを守り、起動のために依存や対象OSを無断変更しない。
4. ビルド → プロセス → 内部描画 → OSのウィンドウ → 実画面 → 必要な操作を区別して確認する。エラー画面でなく目的の画面かを見る。ユーザーが「見えない」と伝えたら表示は未達として調べ、内部画像を根拠に完了扱いしない。
5. 失敗時は配信・接続・描画・OS表示のどこで止まるかを特定する。新しい証拠が得られない同じ再試行を続けず、次に判定する仮説と利用可能な経路を示す。Web等へ切り替える指示が来たら不要になった調査を止め、その経路で開く。

利用者側のウィンドウ・画面を確認できるツールがなければ、確認した段階と未確認の段階を明示する。必要ならユーザーの表示確認を求める。プロセス起動だけで「表示を確認しました」と報告しない。

## 開き直す

対象の専用画面やプロセスを特定し、可能なら通常の終了操作で閉じ、同じ保存状態を使って再起動する。通常ブラウザーを一括終了したり、参加情報を消したり、新しいデータ・ルームを勝手に作らない。

画面の寿命、アプリ内の期限、サーバー等の保存期限は分ける。再起動しても時間が戻るとは限らない。今回の仕様で必要な影響だけを短く伝える。以前の別操作への承認を、共有サービスやOS全体を停止する許可へ広げない。合意済みの同じ操作は再確認で止めない。

## 複数人の発表を準備する場合だけ

- 人数・端末・通信・録画/実演と必要な流れを特定する。参加者の保存領域・認証が独立する構成を確認し、同じプロファイルの別タブを自動的に別人扱いしない。
- 表示用の人数補充、自動操作する相手、背景演出を区別する。準備の依頼を、ゲームAIの追加や通常ルールの変更へ広げない。例外が必要なら影響と具体案を整理する。
- 1画面/複数画面/実写を切り替える場合は、誰が誰と何をしたかがつながる手順にする。編集した動画を、実通信・実機操作の検証結果として説明しない。
- 双方の入力、フォーカス切り替え、戻る・復帰、撮り直しの条件を必要に応じて確認し、実演と予備手順を残す。実際に通していない流れは未確認とする。

報告は、何をどこへ何画面開き、どの表示・操作まで確認したか、残る確認と必要な注意を短く伝える。新しく成功した起動方法・対象・停止方法は環境資料へ記録し、次回も再利用できるようにする。
