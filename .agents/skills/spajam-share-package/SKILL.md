# 開発とプレゼンを分ける共有ZIP

目標は、受け取る人やClaude/Codexが会話履歴を読まず、担当の最初の作業へ着手できること。共有のためにアプリの完成を待たず、未決定の仕様や実装・実機確認済みという事実を作らない。今回の依頼がSkill整備だけなら、本選アプリやスライドの作成へ広げない。

## 共有を始める時点

1. `AGENTS.md`、README、現行の設計・画面方針・担当・検証・素材資料を読む。合意済みのコンセプトと主要導線、主要画面の目的と主操作を引き継ぐ。新規案の未合意部分は、利用可能なら `spajam-flutter-delivery` の認識合わせへつなぐ。
2. 残り時間、受け手の役割、使える資料・ソフト・通信、共有範囲を会話と資料から確認する。不足が作業開始を左右する場合だけまとめて質問する。24時間など既知の予算を聞き直さず、次の共有と発表前の最終差し替え・リハーサルの時点を残り時間に合わせて提案する。
3. 最小の共有条件は、誰のどんな体験か、主要導線、主要画面の方針、確定／暫定／対象外と担当境界が分かること。色・フォント・画面を完全に磨くまで待たない。受け手が依存する未決事項には判断者と確認時点を付け、独立した資料整理やプレゼン構成は先に進められるようにする。

## 共通の事実を引き渡す

[引き継ぎの雛形](assets/team-handoff.md)を、例えば `docs/sharing/checkpoint-01.md` に配置し、現行資料への参照と短い要約で埋める。雛形の未記入欄をそのまま「準備完了」と扱わない。仕様の全文を二重管理せず、この版が何を基準にしているかを示す。

- **コンセプトと話す内容**：利用者・利用場面・課題・提供する体験・主要導線・本選範囲・対象外。プレゼンで伝える中心メッセージ、採用済みの言葉と仮のコピーを区別する。効果・数値・大会条件・発表時間は根拠を確認し、知らない条件を固定しない。
- **スマホ画面**：画面一覧と遷移、各画面の主操作、通常と必要な途中・完了・失敗状態。配色・日本語書体・文字の優先順位・部品・動きの方針と確定度を示す。対象端末は登録を参照し、物理解像度と論理寸法、実測値と仮の確認条件を分ける。
- **視覚資料**：主要画面を画像・ワイヤーフレーム・画面構成表などで示す。画像には画面名・状態・版・実画面／案の区別を付け、実際に開いて対応を確認する。生成イメージを実装済みの画面と扱わず、縦横比や画面文言を資料と揃える。
- **現状と証拠**：機能ごとに `実装済み・確認済み／実装済み・未確認／モック／予定／対象外` を区別し、実データ・サンプルも明記する。操作確認とビルド成功を分け、デモ可能な操作・制約・予備の見せ方を記録する。
- **分担**：開発担当には編集ファイル・共有契約・接続・完成条件・検証方法を、プレゼン担当には中心メッセージ・使用可能な画面や素材・デモ順・主張できる事実・成果物の形式と置き場を渡す。スライド枚数や構成は発表条件に合わせて提案し、未確認の制限を必須にしない。
- **版と更新**：共有ID、作成時刻、基準ブランチ・コミット、未コミット差分、前版からの変更、次の更新担当と時点を記す。変わった画面・文言・機能・デモ順・主張をプレゼン担当が拾えるようにする。

## ZIPを作り、展開側で確かめる

1. [選択リストの雛形](assets/share-plan.json)を実プロジェクトへ合わせる。パスの記入をユーザーへ丸投げせず、AIが資料・素材・必要な共通Skillsと実ファイルを対応付ける。プレゼン作りをFlutter環境の準備に依存させない。追加の開発担当もいる場合だけ、必要なソース・SDK設定・依存ロック・テスト・設定例を含め、起動済みかを区別する。
2. 共有する素材の出典・利用条件を確認し、秘密値・個人設定・実データ・不要な過去資料を選択へ混ぜない。`.git`、SDK本体、キャッシュなどは同梱しない。名前による除外だけで秘密情報が一切ないとは保証せず、選択した設定・資料も確認する。
3. リポジトリのルートから同梱スクリプトを実行する。既存ZIPを上書きせず共有IDを更新する。ZIP作成中だけ対象ファイルを安定させ、作成後の開発は継続できる。

```bash
python3 .agents/skills/spajam-share-package/scripts/build_package.py --plan docs/sharing/share-plan.json --output out/share-packages/checkpoint-01.zip
python3 .agents/skills/spajam-share-package/scripts/build_package.py --verify out/share-packages/checkpoint-01.zip
```

4. 出力は `START_HERE.md`、`MANIFEST.json`、選択したファイルを同じ相対位置で格納した `project/`。マニフェストには版・取得できたGitの基準・未コミットの有無・除外した項目と各ファイルのSHA-256が入る。Gitの値が取得できない場合は未取得とし、ローカルの内容をコミット済みと偽らない。
5. 一時フォルダへ新規展開し、入口から担当資料・主要画面・素材へたどれるか確認する。Claude/Codexで使う場合は `project/` を作業フォルダとして開く。ツールは相対Markdown参照・ZIP内のパス・内容ハッシュを検査するが、画像の意味や実機動作まで検証しない。
6. ZIPはスナップショットで、Git履歴や継続同期ではない。開発者は資料の取得元・基準コミットを確認して担当ブランチを作り、ZIP全体で既存作業を上書きしない。オフラインでZIPを使って編集した場合は変更ファイル・基準版を記録し、再接続後にGit側の担当ブランチで差分を統合する。プレゼンの編集元・返却場所も担当表で決める。
7. 完了報告ではZIPの場所・版・入っているもの・各担当の最初の作業・未確認・次の更新を短く示す。ZIP作成と相手への送信・受領を分け、実際に受け手が確認していなければ「展開試験済み・受け手の確認待ち」とする。明示的な送信依頼なしに他者へ送らない。

## 更新と発表前の照合

共有後に変更があれば同じ資料の変更表を更新し、別版のZIPで渡す。開発と資料作りの担当ファイルを分け、根拠のない仕様追加や仮の画面文言を相互に確定扱いしない。次の受け渡しでは変更のある資料・画面を示し、不要な再合意や全体の作り直しを避ける。

発表前には、実際に使うコミット・端末・画面・主要操作と、スライド・説明・動画が示す状態を照合する。未実装機能、古い文言、未確認の効果を「今動くこと」として話さず、実演できない場合の画像・動画等はその出自を示す。残り時間が少ないときは新しい作り込みより、主要体験・資料・デモの一致とリハーサルを優先する。
