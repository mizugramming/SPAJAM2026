# AIへ渡す開始・分担プロンプト

最初に統合担当が画面遷移・共通データ・保存まで動く基盤を作り、その後に各開発者がページや部品を仕上げます。各開発者は自分の担当を把握している前提です。以下のプロンプトは書き換えず、そのままAIへ渡せます。AIが資料と実際の構成を確認し、会話でまだ伝わっていない担当・変更内容を質問します。

開発者は「宇宙画面の惑星表示を担当しています。惑星をもっと大きく表示したいです」のように答えるだけで構いません。ファイルパスや共通APIはAIが調べます。担当をAIに割り振らせるための質問ではありません。既に会話で伝えたことは聞き直しません。

プロンプトだけで誤変更を完全には防げません。担当ファイルの明示、差分レビュー、CI、マージ保護を併用します。

## 1. 最初に共通基盤を作る人

新しいリポジトリにAGENTSと今回の設計書を置いてから使います。既存アプリの続きに使う場合は、現状を無断で作り直さないことも明記しています。

```text
今回はアプリの初期基盤を作成し、その後に複数人でページ・部品を分担します。

まず次の順番で確認してください。
1. AGENTS.mdと、存在する場合はREADMEおよび対象フォルダの追加指示を読む。
2. READMEや会話から今回の設計書を特定し、最新の決定事項と一緒に読む。
3. Gitの状態と実際のファイル一覧を確認する。既存の実装・設定があれば関連部分を読み、無断で再生成・上書きしない。
4. 設計書の場所、対象環境、実装する範囲、統合先が不明なら、資料や会話で分からない点だけ私に短く質問する。
   例えば実装範囲が不明なら「今回は共通基盤と仮画面まで作りますか、それとも設計書のMVP全体まで作りますか？」と聞く。
   未回答の範囲を勝手に決めて実装せず、回答を待つ間は構成や既存実装の調査を進める。
5. 作成する構成、共通データと画面の接続を短く説明する。

範囲が明確なら、構成説明後はそのまま実装してください。
画面遷移、共通モデル・状態管理・保存処理、各画面の仮UIをつなぎ、起動から保存・再表示まで確認してください。
担当別のソース・素材・テストを分け、素材フォルダを登録してください。
SDKと依存ロックを固定し、環境チェック・CI・PR手順を整えてください。
READMEに担当範囲・統合先・設計書の場所・起動と検証方法を記載してください。
docs/project_structure.mdに実装に即した構成図、責務、共通接続、分担境界を記載してください。
同じ画面を分担する場合は、部品と親画面の組み込み担当、入出力・イベントの契約も整理してください。
実行した検証と未確認事項、各担当へ引き渡せる範囲を報告してください。
今回はPR作成までとし、マージはしないでください。
```

最初から確定できない情報は未確定とします。存在しない資料を読んだことにせず、READMEや構成図は基盤作成の成果物として用意します。

## 2. 各開発者が担当作業を始めるとき

全員が同じ文を使えます。担当と変更内容を会話で答えた後、AIがREADMEと実ファイルから編集範囲を特定します。同じページを分担する場合も、ファイル単位の対応付けはAIが調べます。

```text
私は自分の担当作業を把握しています。担当部分の開発を手伝ってください。
このプロンプトへの記入を求めず、必要な情報は会話で私に質問してください。

編集前に、次の順番で確認してください。
1. AGENTS.mdを読む。
2. READMEを読み、指定された設計書、最新の実装・決定事項、接続資料、開発ガイドを読む。
3. git status --short --branchで作業ブランチと既存変更を確認する。
4. READMEが案内する構成図を読み、rg --filesなどで実際のソース・素材・テスト一覧と照合する。
   隠し設定も必要なものを個別に確認する。生成物・キャッシュ・秘密情報を一括で読み込まない。
5. 担当と変更内容がまだ会話で伝わっていなければ、
   「今回の担当箇所と、そこで実現・変更したいことを教えてください。画面名や部品名で大丈夫です」と質問する。
   片方が分かっている場合は残りだけ質問する。ブランチ名やGitのユーザー名だけで担当を決めない。
   回答が来るまで実装を始めず、読み取り調査を進める。新たな担当割り当ては行わない。
6. 回答をREADMEと実ファイルへ対応付け、担当フォルダの追加指示、対象コード、親画面、共通の接続先、関連テストを読む。
   ファイルパスの記入は求めず、AI側で変更対象を調べる。
   同じ画面の分担境界や組み込み担当が不明な場合だけ、該当する画面・部品を示して追加質問する。
7. 担当範囲、変更予定ファイル、維持する接続、検証方法を短く説明してから実装する。

同じページでも、別担当の部品や親画面を無断で編集しないでください。
共有状態の独自コピーを作らず、既存の共通APIを利用してください。
部品の引数・戻り値・イベントを維持し、変更が必要なら組み込み担当と調整してください。
共通ファイル変更や担当の重複が必要になった場合は、理由と対象を説明してください。
資料と実装が食い違う場合は差を示し、推測で既存機能を巻き戻さないでください。
既に会話で答えた内容は聞き直さないでください。担当と依頼が明確になったら、改めて開始の許可を求めず進めてください。
固定環境で適切な検証を行い、差分・結果・未確認事項を報告してください。
PR先はREADMEの統合ブランチです。今回はPR作成までとし、マージはしないでください。
```

「余白」では[README](../README.md)から[設計書](../yohaku_app_design.md)、[接続資料](feature_integration.md)、[構成図](project_structure.md)、[開発ガイド](development.md)を参照できます。別のアプリでは、そのアプリのREADMEが案内する資料へ置き換えます。

## 3. 別の人の変更を取り込んだ後・AIとの新しい会話

新しい会話では、AIが前の会話を覚えている前提にしません。担当と続きの作業が不明ならAIから質問し、開発者が会話で答えます。

```text
AGENTS.mdとREADME、そこから参照する最新の設計・接続資料を読み直してください。
実際のフォルダ構造とGitの状態も確認してください。
私は担当を把握しているので、会話でまだ伝わっていない場合は
「どの担当箇所の、どの作業から再開しますか？」と質問してください。
既に伝えた内容は聞き直さず、足りない点だけ聞いてください。パスは回答と実ファイルから調べてください。
担当が分かるまでは読み取り調査にとどめ、分かった後に作業ブランチを確認してください。
未コミット変更を保護し、開発ガイドに従って最新の統合先を取り込んでください。
取り込み後の実ファイルと構成図を照合し、担当部分・接続先・関連テストの変更を確認してください。
前の会話や古い構成図だけを根拠に、他の担当の変更を戻さないでください。
変更予定と検証方法を短く示して作業を再開し、取り込み後の状態で検証してください。
今回はPR作成・更新までとし、マージはしないでください。
```
