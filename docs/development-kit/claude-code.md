# Claude Codeとの共同開発

CodexとClaude Codeで、同じ仕様・Skills・検証結果を使います。Claude Codeにも担当機能の調査・設計・実装・検証を一貫して任せられます。AI名だけでフロントエンド／バックエンドの担当を固定せず、得意な提案、現在の作業、残り時間、端末やツールの利用可否で分けます。

## 共有の仕組み

| ファイル | 役割 |
|---|---|
| `AGENTS.md` | 全員の共同開発ルールの正本 |
| `CLAUDE.md` | `@AGENTS.md` の読み込みとClaude固有の入口 |
| `.agents/skills/<name>/` | Codex・Claude共通のSkill本文と参照資料 |
| `.claude/skills/<name>/SKILL.md` | Claudeが認識する短い呼び出し口。本文を複製しない |
| `tool/sync_claude_skills.py` | 呼び出し口の生成と、名前・説明・参照先の同期検証 |

呼び出し口は通常のファイルとしてGitで共有し、Windowsでのシンボリックリンク設定や個人フォルダへのインストールを不要にしています。名前と説明だけはClaudeの選択に必要なため生成し、CIで共通本文とのずれを検出します。

既存の5種を双方で利用できます。Codexの `$spajam-flutter-delivery` は、Claude Codeでは `/spajam-flutter-delivery` です。`spajam-feedback`、`spajam-run-app`、`flutter-fix-layout-issues`、`flutter-add-widget-test` も同じ名前で呼べます。通常の依頼でも説明に応じて選択されますが、狙ったSkillを確実に指定したいときはコマンドを添えます。

## 別PCでの初回準備

Claude Code（CLI、VS Code連携、DesktopのCodeなどでローカルのリポジトリを扱う場合）が対象です。通常のClaudeチャットにURLを渡すだけでは、この作業フォルダや設定は読み込まれません。

1. Claude Codeを公式の手順で用意し、そのPCで自分のアカウントへログインする。認証や個人設定をGitへコピーしない。
2. 初めて取得する場合は、次を1行ずつ実行する。すでに作業コピーがある場合は未コミット変更を保護し、READMEの統合先から専用ブランチを作る。

```bash
git clone --branch honsen https://github.com/mizugramming/SPAJAM2026.git
cd SPAJAM2026
git switch -c feat/claude-first-task
claude
```

3. リポジトリを信頼する画面が出たら内容を確認し、Claude Codeを開始する。`/memory` で共通ルールの読み込みを確認し、`/` の候補に `spajam-flutter-delivery` などが出るか確認する。
4. 次の確認依頼を送り、実際に読んだ資料とできる検証を確認する。担当が決まっていれば、その内容も続けて伝える。

```text
今回は環境確認だけです。CLAUDE.md、AGENTS.md、READMEと、
.agents/skills/spajam-flutter-delivery/SKILL.mdを読み、
現在の統合先、使うSkills、登録済み端末、実行できる検証を短く報告してください。
コード・設定の変更やアプリの新規作成は行わないでください。
```

候補が出なければ、正しい作業フォルダ・ブランチと `.claude/skills/` の有無を先に確認してセッションを再起動します。Skill無効化オプションや組織の制限がある場合は、そのPCの設定を確認します。本文を直接読む方法も使えますが、自動認識を確認できたとは報告しません。

Flutter SDK、Androidのビルド環境、ブラウザー、画像の閲覧、MCP、GitHub CLIなどは別途必要です。Codexで接続できるサービスがClaudeでも接続済みとは扱いません。利用する機能だけそのPCで準備し、使えない検証は記録します。

## 初期開発・担当実装・UI改善

- 初期開発は[穴埋め式プロンプト](initial-prompt.md)の先頭を `/spajam-flutter-delivery` に置き換え、残りは同じ内容を渡す。認識合わせ、主要体験の実装、UIと端末の確認、引き継ぎまで共通手順を使う。
- 基盤完成後の担当実装は[開始・再開プロンプト](../ai_prompts.md)を使う。会話にない担当だけ確認し、既存の設計や基盤を最初から作り直さない。
- UI改善も `/spajam-flutter-delivery` を使う。対象画面、目的、こだわる操作を伝え、画像と実操作で修正前後を比較する。見本がある場合は[UI参考資料](ui-references.md)に従う。
- モデル・思考量はそのPCで利用できるものから選ぶ。設計や難しい不具合では検討を深め、定型修正では対象の資料に絞る。このリポジトリは特定モデルや権限の迂回設定を固定しない。

例えばUIの一部を任せる場合：

```text
/spajam-flutter-delivery
担当の入力画面を改善してください。保存ボタンの意味・文言・押した反応と、
処理中、失敗して再試行する場合の状態を整えてください。
共有仕様と既存のテーマを使い、修正前後の画像と操作で確認してください。
変更範囲と検証結果を、次の開発者が分かる形で残してください。
```

## Codexと分担する

分担は[構成・接続と担当表](../project_structure.md)、引き継ぎは[担当への引き継ぎ](../handoff.md)を正本にします。別PC間でチャット履歴や未pushの作業が自動共有されるとは扱いません。

1. 分けられる機能・部品を選び、目的、編集ファイル、共有API、親画面への組み込み担当、完成条件を先に決める。小さい一体的な変更は1人・1AIで完結させてもよい。
2. 各担当は別の作業ブランチと作業コピーを使う。同じファイルを並行編集せず、テーマ・ルーティング・依存関係などの変更は統合担当へ集約する。
3. 途中でも接続が動く段階で共有契約を確認する。別PCへ渡す場合は、共有可能な作業をコミット・pushし、ブランチ名・コミットSHAと資料を伝える。未コミット差分を渡していない場合は明記する。
4. 実装担当と別のAIでレビューするときは、実装担当の説明だけで判断せず最新の差分と接続先を読む。指摘が仕様変更になる場合は根拠を確認する。AIレビューは人の確認やCIの代わりにしない。
5. PRごとに検証し、統合担当が順番に取り込む。次の担当は最新版を取り込み、接続と操作を再確認する。

レビュー用の入力例（Skillの追加なしで使えます）：

```text
この作業ブランチを、READMEが指定する最新の統合先と比較してレビューしてください。
今回はレビューだけです。ファイル変更・コミット・push・マージは行わないでください。
最初に比較したbase/headのコミットSHAと、未コミット差分を含むかを示してください。
最新の仕様、共有モデル・保存・画面遷移との接続、失敗・再試行・連打・戻る操作、
必要なUIと文言を、実ファイルと関連テストから確認してください。
指摘には場所、起こる条件、利用者への影響、根拠、最小の修正案を添えてください。
疑いと再現した問題、実行した検証と未確認を分け、重要な順に報告してください。
```

別AIへの交代では、目的・担当範囲・関連資料に加え、現在のブランチとSHA、変更内容、検証結果、未解決事項、次の具体的な作業を[引き継ぎ資料](../handoff.md)かPRへ残します。既存の仕様を会話から再生成せず、資料を参照して続けます。

## Skillsを更新したとき

共通本文は `.agents/skills/` だけを編集します。呼び出し口は次のコマンドで更新し、本文・生成差分・参照先を一緒に確認します。追加パッケージは不要です。

```bash
python3 tool/sync_claude_skills.py --write
python3 tool/sync_claude_skills.py --check
python3 tool/sync_claude_skills.py --self-test
python3 tool/check_skills.py
```

`--write` は生成済みの入口と不足分だけを更新し、独自の既存ファイルやシンボリックリンクには書き込みません。共通Skillを削除したときは古い入口を検出して停止するため、参照を調べてから対象の入口も明示的に削除します。

検証ツールの成功は、別PCでのClaudeの自動選択・応答品質・実機操作の成功を意味しません。初回準備の読み込み確認と、実タスクの成果・操作確認を別に行います。

仕様確認日：2026-11-20。[Claude CodeのSkills](https://code.claude.com/docs/en/skills)／[CLAUDE.mdと共通指示の読み込み](https://code.claude.com/docs/en/memory)。別プロジェクトへ再利用する場合は、取得先・ブランチ・資料をそのプロジェクトへ合わせます。
