## 1. アイデア受領と認識合わせ

入力した架空案：

> 「ひとこと栞」を作りたいです。展示会の来場者が、気になった一言を帰り道に片手でメモし、後で一覧で見返し、不要なら削除できます。Android1台、開発者3人、残り6時間、外部サービスなし。静かで読みやすい雰囲気にしたいです。

6時間・3人は試行用の条件で、大会の規約ではありません。新アプリの既存ファイル・SDKは未指定という条件で試しました。

適用結果：誰・場面・課題・導線・OS・人数は質問し直さず、永続化と本選で動かす範囲を合わせる質問に絞りました。

> 展示会で出会った言葉を忘れないため、入力 → この端末に保存 → 一覧で見返す → 削除を主要導線とします。再起動後も残す端末保存を提案します。今回はこの範囲でよいですか。共有・アカウント・画像添付は対象外を提案します。
> 完成条件は、この導線と失敗時の入力保持が動き、別の開発者が起動・担当開発を再現できることです。技術環境は実フォルダを確認し、なければ固定環境の具体案を提示します。

ここではコード着手を保留しました。残り時間を根拠に合意済みとは扱いませんでした。対象大会の持ち込み条件も未確認のまま記録しました。

次の段階へ進むための**架空の回答**：

> その範囲でお願いします。再起動後もこの端末に残してください。共有は不要です。保存処理と共通部は開発者A、入力はB、一覧と削除はCが担当します。

## 2. 初期実装の計画への適用

提案した構成は次の範囲です。以下のパスは計画上の例で、今回のリポジトリに作成したFlutterアプリではありません。

| 順序 | 作るもの・接続 | 確認する結果 |
|---|---|---|
| 0 | 対象リポジトリ・SDK・ロック・端末を調査し固定。README、設計・担当表を確定 | 準備済み環境を使い、旧アプリのSDKやブランチを自動採用しない |
| 1 | A：起動・親画面・テーマ、Note型、単一のNotesController、端末保存と注入 | 起動→読み込み→空一覧。保存・復元・削除と失敗が共通契約で動く |
| 2 | B：入力、C：一覧と削除UI。親への組み込みはA | 入力→保存成功→一覧反映→削除→再起動の一周 |
| 3 | UI/文言・小さい領域・文字拡大・キーボードと戻る・連打を確認し修正 | 入力保持、二重保存防止、主要操作への到達性 |
| 4 | 起動手順・確認結果・担当別の残作業を引き渡す | 担当者の起動再現を記録。未実施なら完了条件に残す |

状態管理は、単一の小さなControllerを共有し、画面ごとに一覧をコピーしない案としました。新しいDI・ルーティング・モデル生成パッケージを必須にしませんでした。保存の依存は環境を見て選び、共通部担当Aが管理する計画です。

共有契約案：

- `lib/notes/note.dart`：`Note(id, text, createdAt)`。IDは再試行で同じ記録を二重作成しない単位、日時は保存時UTC・表示時ローカル。空文字を保存しない。
- `lib/notes/notes_controller.dart`：`saveDraft(draftId, text)` と `deleteNote(id)`、一覧・処理中・失敗を公開。同じ操作の重複を防ぎ、保存成功後に確定一覧を更新する。
- `lib/notes/note_store.dart`：端末保存・読込・削除。失敗時は前回の確定一覧と編集中の入力を保つ。保存形式はAが定義し、B/Cは独自の保存先を作らない。
- `lib/features/editor/note_editor.dart`：保存用コールバックを受け、失敗時に入力を消さない。`lib/features/list/note_list.dart`：同じNote一覧と削除用コールバックを受ける。

例：一覧側は `onDelete(note.id)` を通知する。画面で独自に永続化せず、成功後の共有状態を再表示する。削除の実装と失敗表示は基盤の契約と合わせる。

## 3. UI・文言の判断への適用

「帰り道に片手」「静かで読みやすい」を、淡い紙色、濃い本文色、一つの目立つ保存操作、読みやすい本文、装飾を抑えた結果表示へ対応付けました。特定フォント・412×900の枠・ゲームの演出は採用しませんでした。

| 状態・候補 | 適用した判断 |
|---|---|
| 初期の空一覧 | 「残しておきたい言葉をメモしましょう」＋「メモを書く」。読む目的と次の操作がある |
| 主操作 | 「この端末に保存」。実際の保存先と一致し、通信共有と誤解させない |
| 保存中 | 「保存しています」＋連続実行を止める。確定完了とは扱わない |
| 保存失敗 | 「保存できませんでした。入力は残っています」＋「もう一度保存」。保持が実装されていることを確認条件にする |
| 「みんなに共有しました」 | 外部共有がないので不採用。端末保存の成功だけを伝える |
| 「Repositoryの初期実装です」 | 開発者向けなので画面へ入れず、開発資料へ記録 |
| 「1分で記憶力が上がる」 | 根拠がなく、操作にも不要なので不採用 |
| 長文・文字拡大・キーボード | 固定高さを増やすのでなく、親制約とスクロールで入力・保存へ到達させる |
| 戻る・削除 | 入力破棄の扱いを明示。削除は対象を確認できる操作にし、キャンセルを用意 |

スクリーンショットが存在しないため、見た目を確認済みにはしませんでした。実装時の確認計画として、例えば320×568論理領域・文字拡大・キーボード表示で入力画面と保存失敗を撮り、画像を開いて修正後に再撮影する手順を指定しました。この数値は試験例で、本番の固定寸法ではありません。
