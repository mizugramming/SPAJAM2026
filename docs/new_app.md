# 新しいアプリを共同開発する準備

`AGENTS.md` はそのまま再利用し、アプリごとにREADMEと設計書を用意します。ただし文書だけでは起動できません。統合担当が実行できる共通基盤と検証環境を一度作り、全員が同じコミットから分担を始めます。

## 最初に用意するもの

| 用意するもの | 内容 |
|---|---|
| `AGENTS.md` | このリポジトリの共通ルールをコピー。アプリ仕様やバージョン数値は書き込まない |
| `README.md` | アプリ概要、設計書へのリンク、担当者・担当フォルダ、統合先・リリース先、起動・検証手順 |
| `docs/app_design.md` | 下記の設計項目。未確定事項は未確定と記載 |
| 実行できる雛形 | エントリーポイント、対象プラットフォーム、画面遷移、共通モデル・状態・保存処理、各担当の仮画面 |
| 環境・依存設定 | SDK固定設定、環境チェック、依存宣言とロック、改行設定・生成物の除外 |
| 素材用フォルダ | 共通と担当別に分割し、登録を済ませる。空フォルダは `.gitkeep` などで共有 |
| 検証・GitHub設定 | 接続を確認するテスト、CI、PRテンプレート、有効なブランチ保護 |

### 設計書に書く内容

以下を `docs/app_design.md` の見出しとして使えます。

1. **目的とMVP**：誰の何を解決するか、今回作る範囲。
2. **対象環境**：Android/Webなど、スマホの画面条件、マウス・タッチ操作。
3. **画面一覧と遷移**：各画面の表示内容・操作・行き先。参考画像があれば場所も示す。
4. **共有データ**：項目・型・ID・日時の扱い、更新する画面と表示する画面。
5. **保存と外部連携**：端末内かサーバーか、再起動後の復元、認証・権限、失敗時の動作。キー本体は書かない。
6. **素材とデザイン**：画像・フォントの配置、担当、出典、未用意素材の仮表示。
7. **分担と接続契約**：担当フォルダ、共通API、統合担当。READMEの担当表と食い違わせない。
8. **完成条件**：具体的な操作と期待結果。例「画面Aで追加した記録が画面Bへ反映され、再起動しても残る」。
9. **未確定事項・決定履歴**：仕様変更の日付と採用した内容。初期案だけで実装を巻き戻さない。

## Flutterで今回と同じ環境を使う場合

Flutter 3.41.5 / 同梱Dart 3.11.3を使う例です。新しいアプリで別のSDKを採用する場合は、統合担当が全設定とCIを揃えます。

1. FVMを導入して指定SDKを用意する。AndroidはJDK 17と必要なSDKも端末側へ導入する。
2. **既存プロジェクトの外側**で、新しい名前のフォルダへ雛形を生成する。以下は `my_new_app` がまだ存在しない場合の例。`com.example` は本番用の組織IDへ置き換える。

   ```bash
   fvm install 3.41.5
   fvm spawn 3.41.5 create --platforms=android,web --org com.example --project-name my_new_app my_new_app
   cd my_new_app
   ```

3. ルールと設計書を置き、下表の設定を準備する。新規生成した `pubspec.lock` を使い、余白の依存関係やロックを丸ごと流用しない。
4. `fvm use 3.41.5` → `fvm dart tool/check_environment.dart` → `fvm flutter pub get --enforce-lockfile` → `fvm flutter run -d chrome` で起動する。
5. 統合担当が画面・素材の担当フォルダ、共通データ、仮画面間の接続、保存処理を実装する。全体検証とCI成功後、そのコミットから各担当の作業ブランチを作る。

`flutter create` は既存アプリにもファイルを再生成するため、共同開発中のルートで修復目的に実行しません。上記は新規フォルダ専用です。雛形の生成だけでは設計書の機能は実装されません。

### このリポジトリから再利用する設定

| 対象 | 新規アプリでの扱い |
|---|---|
| `.fvmrc`, `tool/toolchain.json`, `tool/check_environment.dart`, `test/tool/check_environment_test.dart` | 同じ環境ならセットでコピー。SDK変更時は整合する値とチェックへ更新 |
| `.gitattributes`, `.vscode/settings.json` | 内容を確認して再利用。FVMのSDKパスを設定 |
| `.gitignore` | 新規生成したものに `.fvm/` など必要な除外を反映 |
| `.github/workflows/flutter.yml` | コピー後、対象プラットフォーム・テスト・ディレクトリに合わせる。Androidの生成設定とSDK/Gradle等の整合も確認 |
| `.github/PULL_REQUEST_TEMPLATE.md` | 担当と統合ブランチ名を新プロジェクト用に変更 |
| `.github/*-ruleset.json` | ブランチ名・必要チェック・レビュー人数を決め、**新リポジトリのGitHub側に適用**。コピーだけでは保護されない |
| `CLAUDE.md`, `.github/copilot-instructions.md` | 利用するAI向けに参照先を確認して再利用 |

CIを再利用する場合は `lib/`・`test/`・`tool/` を用意し、雛形のテストを実際の共通基盤に合わせます。初回の依存追加・ロック生成は統合担当が行い、分担開始後はロックを固定して取得します。READMEにチェックコマンドを明記してください。

新規生成されたアプリID、依存関係、プラットフォーム設定を基準にします。余白の `lib/`・プラットフォーム設定・`.git/`・ユーザーデータ・署名鍵はコピーしません。SDK本体、Android SDK、キャッシュもリポジトリへ入れません。必要な秘密情報があるアプリは、値を含まない設定例と端末・CIへの設定手順を用意します。

## 分担開始前の完了条件

- 新しくcloneした環境で、READMEどおりにSDK・依存関係を準備し、アプリを起動できる。
- 仮デザインでも全画面を移動でき、同じ共通データの追加・表示・保存・復元がつながる。
- 各担当の素材フォルダが登録済みで、共通設定を触らずに画像を追加できる。
- 解析・テスト・対象プラットフォームのビルドがCIで成功する。
- 統合ブランチを作成し、PR・必須チェック・最新状態・force push禁止の保護が有効。保護設定ファイルの配置だけで済ませない。
- 全員が同じ基盤を取り込み、1人・1タスクのブランチで作業できる。

## AIへ渡す開始依頼

```text
AGENTS.mdを共通ルールとして読み、README.mdとdocs/app_design.mdを確認してください。
今回は新規アプリの共通基盤を作ってください。
指定SDK・依存ロック・環境チェック・CIを整え、担当別のソース・素材・テスト用フォルダを用意してください。
画面遷移、共通モデル・状態管理・保存処理をつなぎ、仮画面で一連の操作ができる状態にしてください。
画像は担当フォルダへ追加できるよう登録し、出典の記録方法も用意してください。
READMEに担当範囲・統合先・セットアップ・起動・検証方法を記載してください。
実施した検証と未確認の環境を報告してください。今回はPR作成までで、マージはしないでください。
```

これは基盤作成を依頼する文です。アプリ全機能の実装も依頼する場合は、設計書のどこまで実装するかを明示します。
