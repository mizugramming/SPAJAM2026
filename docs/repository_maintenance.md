# このリポジトリの運用

この文書はSPAJAM2026の管理用です。別アプリへコピーする共通セットには含めません。

## ブランチの役割

| ブランチ | 役割 | 作業時の案内 |
|---|---|---|
| `main` | アプリ共通のルール・担当作業プロンプト・資料の雛形 | [ルートREADME](../README.md)。アプリ実装を置かない |
| `test-1` | まよいクエストの統合先 | [対象README](https://github.com/mizugramming/SPAJAM2026/blob/test-1/README.md) |
| `honban` | つなぐんの統合先 | [対象README](https://github.com/mizugramming/SPAJAM2026/blob/honban/README.md) |
| `rehearsal/02` | 余白の統合先 | [対象README](https://github.com/mizugramming/SPAJAM2026/blob/rehearsal/02/README.md) |
| `rehearsal/01` | 初回練習アプリの保管先 | [ソース](https://github.com/mizugramming/SPAJAM2026/tree/rehearsal/01)。作業を続ける場合は統合先を確認 |

作業ブランチ名だけで対象を決めません。対象ブランチのREADME・実装・PRの宛先を確認します。アプリごとのSDK・依存ロック・CIもそのブランチで管理します。

日付ごとの確認結果は[2026-11-04の棚卸し](repository_inventory_20261104.md)に分けています。作業再開時にはリモートとPRの最新状態を確認してください。

mainとアプリの開発ブランチは、ブランチ全体を相互にマージしません。mainの削除差分をアプリへ入れたり、アプリの実装をmainへ戻したりしないためです。異なるアプリの統合先同士も同様です。共通ルールを更新するときは、必要な共通ファイルの差分だけを各作業ブランチへ反映し、PRで確認します。

新しいアプリは別のプロジェクトとして基盤を用意し、共通セットをファイル単位でコピーします。古いアプリの作業ブランチを新しいアプリの開始点にしません。

## mainの変更とCI

共通キットの作業ブランチからmain向けPRを作ります。`.github/workflows/check.yml` の `check` は、必要な資料・ローカルリンク・アプリファイルの混入と差分を検査します。アプリが存在しないmainでFlutterのビルドは実行しません。余白のブランチのFlutter CIは維持します。

新しいアプリにはそのアプリ用のCIとブランチ保護を用意します。このキットのチェック成功を、アプリの動作確認済みという意味で使わないでください。

承認数・必須チェック・ブランチ保護は、マージ前にGitHubの有効な設定を確認します。過去の資料にある例外権限を、今回の操作許可として扱いません。承認待ちやCI失敗を理由に保護を迂回しません。

## PRと作業ブランチの整理

1. 最新のリモートを取得し、対象アプリ・統合先・開いているPR・ブランチ先端を確認します。
2. 同じ変更のPRが複数ある場合は、正しい宛先のPRを残します。閉じるPRには理由と継続先・保存先を記録し、ソースを保持します。
3. 古いブランチは、先端まで統合先に含まれているかを履歴で確認します。PRがマージ済みでも、その後の追加コミットがあれば未統合として扱います。
4. 開いているPR、未統合の変更、継続利用する担当ブランチがあるものは残します。判断がつかないものは棚卸しへ記録します。
5. 削除候補は、保存先と先端コミットを記録し、削除直前にも先端が変わっていないことを確認します。統合先や保存タグは削除しません。

`git fetch --prune origin` は、リモートで既に削除されたブランチの追跡情報をローカルから整理する操作です。リモートの作業ブランチ自体は削除しません。

PRの説明はルートのテンプレートを使い、アプリの場合も共通キットの場合も対象と宛先を明記します。過去のアプリ・練習PRをmainへそのままマージしないでください。
