# このリポジトリの運用

この文書はSPAJAM2026の管理用です。別アプリへコピーする共通セットには含めません。

## ブランチの役割

- `honban`：つなぐんの本番アプリ基盤・設計・固定SDK・アプリ用CI。作業ブランチのPR先。`main`とはブランチ全体を相互マージしません。
- `main`：アプリ共通のルール・担当作業プロンプト・資料の雛形。アプリ実装を置きません。
- `rehearsal/02`：余白アプリの開発内容。環境固定・依存ロック・アプリ用CIもここにあります。
- `docs/reusable-development-rulebook` / PR #23：余白向けの担当・環境・接続資料の整備。統合先は `rehearsal/02` です。

honbanは開発キットから派生した本番用ブランチです。現在の具体的手順は [README](../README.md) と [開発手順](development.md) を優先します。以下の過去設定記録は、現在のhonban保護設定を保証しません。

mainとアプリの開発ブランチは、ブランチ全体を相互にマージしません。mainの削除差分を余白へ入れたり、余白の実装をmainへ戻したりしないためです。共通ルールを更新するときは、必要な共通ファイルの差分だけを各作業ブランチへ反映し、PRで確認します。

新しいアプリは別のプロジェクトとして基盤を用意し、共通セットをファイル単位でコピーします。古いアプリの作業ブランチを新しいアプリの開始点にしません。

## mainの変更とCI（共通キット側の説明）

honbanでは同名の `check` をアプリ向けへ置き換え、文書・SDK・解析・テスト・Web/Androidビルドを検証します。GitHubのルールセット変更は別作業です。

共通キットの作業ブランチからmain向けPRを作ります。`.github/workflows/check.yml` の `check` は、必要な資料・ローカルリンク・アプリファイルの混入と差分を検査します。アプリが存在しないmainでFlutterのビルドは実行しません。余白のブランチのFlutter CIは維持します。

新しいアプリにはそのアプリ用のCIとブランチ保護を用意します。このキットのチェック成功を、アプリの動作確認済みという意味で使わないでください。

2026-09-24のGitHub API確認では、mainの必須承認は1人、rehearsal/02は0人です。両方でPR・最新の統合先への追従・必須チェック `check`・レビュー会話の解決が要求されています。これは確認時点の設定であり、マージ前には有効な設定を再確認します。

所有者 `mizugramming` にはPR経由のルールセット迂回権限が残っていますが、通常の開発・AIへのマージ依頼では使用しません。承認待ちやCI失敗を理由に `--admin` や保護解除で進めないでください。資料の変更だけではGitHubの権限は変わりません。

同日の確認ではマージ後のブランチ自動削除が有効です。番号ブランチを継続利用する新しいアプリでは、管理者が自動削除を無効にし、merge commit方式を使用する設定・運用を確認してから引き渡します。このキットの修正で現在のGitHub設定を変更したわけではありません。

過去のアプリ・練習PRをmainへそのままマージしないでください。整理時点でmain向けに残っているPR #9・#10も、担当者と目的・統合先を確認してから扱います。
