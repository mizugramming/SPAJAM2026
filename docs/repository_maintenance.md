# このリポジトリの運用

この文書はSPAJAM2026の管理用です。別アプリへコピーする共通セットには含めません。

## ブランチの役割

- `main`：アプリ共通のルール・担当作業プロンプト・資料の雛形。アプリ実装を置きません。
- `honsen`：本選アプリの開発・統合先。`main` のコミット `72e4b951599f95bb26eb8fc7e09ab18ed1b42349` を起点に準備します。本選の作業PRはこのブランチへ向けます。
- `rehearsal/02`：余白アプリの開発内容。環境固定・依存ロック・アプリ用CIもここにあります。
- `docs/reusable-development-rulebook` / PR #23：余白向けの担当・環境・接続資料の整備。統合先は `rehearsal/02` です。

mainとアプリの開発ブランチは、ブランチ全体を相互にマージしません。mainの削除差分を余白へ入れたり、余白の実装をmainへ戻したりしないためです。共通ルールを更新するときは、必要な共通ファイルの差分だけを各作業ブランチへ反映し、PRで確認します。

今回の本選アプリは、このリポジトリ内の `honsen` ブランチで基盤を用意します。`main` の共通キットを起点にし、古いアプリのコードや作業ブランチを流用しません。別リポジトリへ再利用する場合のコピー手順は [共通セットの再利用](reuse_rules.md) を参照します。

## mainの変更とCI

共通キットの作業ブランチからmain向けPRを作ります。`main` 上の `.github/workflows/check.yml` の `check` は、必要な資料・ローカルリンク・アプリファイルの混入と差分を検査します。アプリが存在しないmainでFlutterのビルドは実行しません。余白のブランチのFlutter CIは維持します。

新しいアプリにはそのアプリ用のCIとブランチ保護を用意します。このキットのチェック成功を、アプリの動作確認済みという意味で使わないでください。

### main・rehearsal/02のマージ方針

`main` と `rehearsal/02` はPRを通して変更します。必要なレビュー承認数は0です。書き込み権限のあるメンバーは、自分が作成したPRも、ほかのメンバーによる承認を待たずにマージできます。レビューは任意で依頼できます。

マージ前に、次を確認します。

- PRの統合先が正しく、最新の統合先を作業ブランチへ取り込んでいる。
- 最新コミットの必須CIチェック `check` が成功し、競合がない。
- PR内の未解決のレビュー会話がない。

条件を満たしたら、GitHubの通常のマージ操作、または次のコマンドを使います。

```bash
gh pr checks PR番号 --required --watch
gh pr merge PR番号 --merge
```

各コマンドは1行ずつ実行します。チェックが失敗・実行中・キャンセル・未実施の場合は、原因を確認して解決し、成功を確認してからマージします。他のPRが先にマージされたら、最新の統合先を取り込み、検証・push・必須チェックの確認をやり直します。

通常のマージに管理者権限による迂回は不要です。所有者に設定されているPR限定の例外権限は、日常のマージ手順には使いません。PR経由・必須チェック・未解決会話の解消・force pushとブランチ削除を制限する保護は引き続き有効です。

過去のアプリ・練習PRをmainへそのままマージしないでください。整理時点でmain向けに残っているPR #9・#10も、担当者と目的・統合先を確認してから扱います。

## honsenの開発とマージ

本選の作業ブランチは最新の `origin/honsen` から作り、PRの `base` は `honsen` にします。`feat/<内容>`、`fix/<内容>`、`docs/<内容>` を使い、1人・1タスクで分けます。通常の更新でも取り込む統合先は `origin/honsen` です。

書き込み権限を持つメンバーは、自分のPRも他者の承認を待たずにマージする運用です。マージする人が最新のCI成功、差分、競合、未解決のレビュー会話を確認します。`main` の保護設定が別ブランチへ自動適用されるとは扱いません。

`honsen` の `check` はSkills・self-test・空白を検査します。`tool/check_kit.py` は保持しますが、本選の作業ブランチと `honsen` のCIでは実行しません。`main` 宛てのPRではキット専用検査を実行し、アプリファイルの混入を確認します。アプリ基盤の作成時に、そのSDK・依存ロックに合う解析・テスト・ビルドを追加します。

設計・SDK・担当・起動方法が未決定であることと、現在の実行可能な確認手順は[本選の開発手順](development.md)に記録します。本選の変更を `main` へブランチごとマージせず、必要な共通ルールだけをファイル単位で扱います。
