## PRの大きさと監査

ページ単位のPRでよく、細かい見た目の修正ごとの分割は不要です。共有データ・保存・画面遷移との接続が不確かな場合は「最小の接続が動く段階」と「ページ完成」に分けます。既存操作を壊す未完成コードはマージせず、必要ならDraft PRで共有します。

通常PRは作成者以外の人1人の承認を基本案とします。採用する人数は上のCI・PR・マージ欄に記入し、GitHubの有効なルールと一致させます。共通モデル・保存形式・依存関係の変更は、影響する担当にも確認を依頼します。AI監査は人の承認とCIの代用にしません。

監査担当のAIには、対象リポジトリとPR番号を添えて次を渡します。監査だけでは承認の投稿やマージは許可しません。

```text
このPRを読み取りで監査してください。AGENTS.mdとREADME、設計・接続・開発資料を読み、
PRの宛先、最新の差分、実際の接続先と関連テスト、CI結果を確認してください。
担当外変更、保存形式・共通APIの不整合、入力消失・二重保存、エラー時の挙動、
素材の参照漏れ、未検証の主要操作を確認してください。
指摘は重要度、ファイル・行、問題が起こる条件、影響、修正案を示してください。
問題を見つけなかった場合も監査したコミットと未確認事項を報告してください。
ファイル変更・承認の投稿・マージは行わないでください。
```

重大な指摘を修正し、最新の差分を再監査・再検証してから人が仕様と操作を確認します。AIの推測は再現条件やコードで確かめ、指摘を無条件に採用しません。

## マージ直前と発表前

- 統合担当がリポジトリ・PR番号・宛先・変更一覧を確認する。宛先違いや大量の無関係な差分があれば、原因と修正後の差分を確認する。
- 先行PRが入ったら後続は最新の統合先を取り込み、依存取得・検証・push・監査と承認の確認をやり直す。
- 最新コミットの必須チェック・必要な人の承認・競合なし・レビュー会話の解決を確認する。チェックなしや必要な検証のskipを成功扱いにしない。
- マージは対象リポジトリとPR番号を明示し、1件ずつ行う。所有者も通常は保護を迂回しない。

## 作業の保存・競合・エラー時の対応

### 取り込み前の保存

エディタでの保存だけではGit上の作業は保護されません。自分の作業ブランチで、変更したファイルと秘密情報・生成物が含まれないことを確認して途中コミットします。対象パスは実際の変更に置き換えます。

```bash
git status --short --branch
git diff
git add -- "変更したファイルのパス"
git diff --cached
git commit -m "wip: 担当作業の途中保存"
git status --short
```

他人の変更は混ぜず、未追跡ファイルも確認します。変更がなければコミットは不要です。必要な変更を保存し、作業ツリーがクリーンになってから切り替え・取り込みを行います。秘密情報や保存方法が不明な変更が残る場合は、そのまま取り込まず統合担当へ相談します。既に途中コミットした変更も、PR提出前には全体を検証・レビューします。

### mergeが競合した場合

1. 後続の依存取得・起動・pushを止め、`git status` と `git diff --name-only --diff-filter=U` で競合ファイルを確認する。
2. 自分の担当ファイルで両方の意図が明確な場合だけ、両方の必要な変更を残して解決する。一括のours/theirsや競合マーカーの削除だけで済ませない。
3. 共通モデル・ルーター・ロック・他担当のコード・画像は、双方の担当と統合担当へ、ファイル名・双方の変更目的・迷っている点を渡す。未解決の同じ作業ツリーで別作業を始めない。
4. 解決したファイルだけ `git add -- "解決したファイルのパス"` で登録する。`git diff --name-only --diff-filter=U` の出力が空であること、`git diff --cached` と `git diff --cached --check` を確認する。
5. merge中であることを `git status` で確認し、`git commit -m "merge: 統合先の変更を取り込み"` で完了する。依存取得・解析・テスト・必要なビルドと接続確認をやり直してからpushする。

ロックファイルは手で行を混ぜず、統合担当が固定環境で依存宣言を解決して再生成します。判断待ちでmergeを取りやめる場合は、取り込み前の変更が保存済みであることを確認し、競合解決中の必要な編集を別途保護してから `git merge --abort` を使います。取り込み前から未保存変更があった場合は安易にabortせず、現状の保護を先に相談します。

### よくある停止理由

| 状況 | 次にすること |
|---|---|
| 番号ブランチが既に存在する | 作り直さず既存ブランチへ切り替える。別PCはREADMEのリモート取得手順を使う |
| `git pull --ff-only` / pushが履歴の分岐で失敗 | 同じ番号の別PC・別作業を確認し、統合担当と履歴を調べる。force pushしない |
| `nothing to commit` | `git status` とコミット済み差分を確認する。保存済みなら検証後にpushへ進む |
| SDK・依存ロック・Javaなどのエラー | 指定環境との違いを確認し、設定を書き換えず統合担当へエラーを共有する |
| CIが失敗・起動しない・必要なチェックがない | 該当ログと最新コミットを確認する。保護を解除せず統合担当が原因を調べる |
| AIが共通ファイル変更を必要と判断 | 理由・対象・影響を統合担当へ渡す。必要な共通変更を先に統合してから取り込む |

## 引き渡し前の小さな統合練習

本番用基盤で、担当者2人がそれぞれ自分の別ファイルへ小さな動作変更を加え、通常のPR・CI・監査・承認・マージを一巡させます。後続担当が先行PRを取り込み、マージ後も同じ番号ブランチで次の差分だけをPRにできることを確認します。練習用変更が不要なら取り消しPRで戻します。

確認するGitHub設定は、PR必須・採用した承認数・新しい変更での再承認方針・最新統合先への追従・想定したCI必須・未解決会話の扱い・迂回権限・マージ方式・自動削除です。設定の確認日と結果を上の欄へ記録します。資料チェックだけで各PCやGitHub上の運用を検証済みとは扱いません。
